# P2-12 台词停顿标签：让台词有呼吸感

## 差距（airi 怎么做）

airi 从流式文本里统一解析三种控制事件（`airi/packages/pipelines-audio/src/llm-streaming-control/`：act / call / **delay**）。delay 是其中最容易被低估的：AI 台词「一口气念完」的机器感，很大一部分来自没有语义停顿——真人在问句后、转折前、想说重要话前都会顿。

## 我们的现状

TTS 按句合成、句间天然有合成间隙，但**句内与句间的停顿时长不受控**：LLM 想表达犹豫、强调、卖关子时没有表达手段（只能靠标点碰运气）。协议基础是现成的：说话语气标签与动作标签（`【动作：点头】`）已经跑通了「标签先行、不朗读、不进 UI、不进历史」的通道（ADR 0001），停顿只是这条通道上的第三个词。

## 方案（若做）

1. **标签语法**：与动作标签同族，句前内联 `【停顿：短】`（闭集：短≈300ms / 中≈700ms / 长≈1200ms，词表三档足够）。
2. **执行位置在前端播放层**：`useAudioQueue` 按序播放时，遇到停顿标记在下一句音频起播前插入静音——不改 TTS（SBV2 不感知停顿）、不改服务端合成节奏，是纯播放层概念。
3. **服务端职责同动作标签**：解析进 SSE 事件（如 `{"type":"pause","duration":"short"}` 或搭在 sentence 事件的元数据里）、从可朗读文本剥除、不进对话历史；节流同 MotionPolicy 风格（每轮至多 2 个，防 LLM 滥用停顿把节奏打碎）。
4. **prompt 侧**：动作/说话语气标签的标签说明里加一行停顿标签的用法与「缺省不用」导向——停顿是味精，不是主料。

## 验收

- 单测：标签解析与剥除、节流、事件时序（停顿事件与前后 sentence 的顺序）。
- 听感轨盲测：带停顿的台词 vs 不带，问句后停顿/强调前停顿的语义匹配；无「念 PPT 式匀速」感提升。

## 为什么是 P2

- 需要动 LLM 的标签词表与 prompt（eval-set 回归要跑），且收益是「锦上添花」档——先做完 P0/P1 的硬伤再上味精。
- 停顿时长三档的具体数值需要听感调参，不是纯工程决定。

## 规模

S-M（服务端解析节流 S；前端播放层插入与听感调参 M）。
