# P0-2 Jev/Kev 表演情绪提前发起（流尾才问 → 首句就问）

**状态（2026-09-24）：改进方案已在本地工作树，本篇移入 `done/`；尚未提交，设备验收未做。** `WebChatService.stream()` 在首个清洗后句子触发一次 Jev/Kev 请求，`ask_messages` 把输入标明为未完成回复的前缀；单调度循环在判定完成后立即交付 performance，生成结束时取消未完成的辅助判定。中文首句/全文对照和起播前覆盖率仍要测。

## 差距（airi 怎么做）

airi 的表演控制是**流内即时**的：`airi/packages/pipelines-audio/src/llm-streaming-control/` 从流式 token 里解析 `<|ACT {"emotion":...,"motion":...}|>` 控制事件，与 TTS 分句同序投递——情绪/动作在播放到那一句之前就已经到位。

## 我们的现状

职责划分不同（ADR 0001：动作/说话语气由 LLM 标签先行，表演情绪由 System One 判定）。实施前的问题在**发起时机**：

- `232b7c6` 的 `frontend/web.py`：`jev_task` 在 LLM 流完全结束、尾句全部 flush 后才创建。
- 同一版本在流尾等待判定，覆盖事件在 `done` 前才发出。

结果是：整轮流式输出期间，前端一直用「说话语气兜底」的表演情绪（web.py:155-158 先发一个 fallback performance 事件），Jev 的真实判定最多覆盖到还在播的尾部几句。而 2 秒超时（`dialogue/jev_client.py`）完全来得及在 LLM 还在流式输出时就返回。

## 改进方案

**Jev/Kev 输入允许部分文本。** 旧接口收到完整回复；本地实现传入首句并标明这是未完成回复的前缀。短前缀与全文的判定是否一致仍需中文样本检验：

1. 首句产出时（说话语气标签解析完成后）即发起：输入 = history + 清洗后的首句文本。
2. 判定完成时立即下发覆盖事件；仅把派发点前移而仍在流尾等待，会错过首句播放。本地调度在 LLM/TTS 等待期间也检查判定结果。
3. Jev 不可用/超时/低置信的行为完全不变（回落说话语气、60s 失败冷却）。

目标时序：首句 TTS 合成与 Jev/Kev 判定并发；结果若早于实际起播则覆盖首句，否则从到达时起覆盖剩余播放。2 秒超时与模型延迟不能保证每轮起播前覆盖，短回复可能在辅助判定完成前结束。

## 验收

- `tests/test_jev_client.py`：首句输入被明确标为未完成回复前缀；拿相同样本比较首句与全文判定差异，不能要求它们总是一致。
- `tests/test_web.py`：覆盖首句发起、LLM/TTS 等待中交付、取消、短回复迟到结果与回落路径。
- 端到端：服务端记录 `jev_dispatch → jev_done`；浏览器另记首句 `playing` 和 performance 实际生效时间，报告起播前覆盖率，不能只用「早于流结束」代替。

## 边界与风险

- **首句判错的风险**：首句文本短，情绪信息可能不足。回落只处理不可用、低置信与超时，不能自动纠正高置信误判；需按日常、沉重话题、玩笑挑衅分别评估误接受率。
- 不改成 airi 的「LLM 流内 ACT token」方案：那会把表演情绪判定权交回 LLM，违反 CONTEXT.md 的控制归属约定（表演情绪归 System One）。
- 本地 Kev 延迟须按实际模型、中文输入和硬件测量；上游报告不能作为本项目的百毫秒保证。
