# P1-7 用户长期记忆：遗忘曲线检索的「她记得你」

**状态（2026-09-23，本地工作树）：默认关闭的基础版已接线。** 用户在记录面板启用后，系统只从明确的“我叫/我的名字是/我喜欢/我不喜欢”提取字面短事实，存入同一 SQLite；可查看来源、逐条删除、关闭召回，清空会话时一并删除。当前是可解释的规则抽取与时间衰减排序，尚无 LLM 抽取、向量检索、手动纠错或跨设备鉴权。

## 差距（airi 怎么做）

airi 的记忆设计（devlog `docs/content/en/blog/DevLog-2025.04.06`、`DevLog-2025.04.14`；注意 pgvector 实现已外移成 stub，这是设计差距不是代码差距）最有价值的想法是**无状态遗忘曲线**：

- 不跑定时任务更新分数，检索时用「当前时间」对每条记忆的 half-life 施加衰减函数**现算**得分；
- 排序 = `1.2 × 向量相似度 + 0.2 × 时间相关度`（权重可调）；
- 每次被召回 `retrieval_count + 1`，越常提起越不容易忘——强化学习式的记忆巩固；
- 常被召回、半衰期长的条目自然沉淀为长期记忆，无需显式分层迁移。

## 我们的现状

`dialogue/memory.py`：最近 8 轮原文 + ≥12 轮触发 LLM 滚动摘要。摘要是有损压缩，**细节（用户的名字、偏好、告诉过她的事）在滚动中被磨掉**。`docs/persona/facts-kb.json` 的关键词 RAG 是**她的**公开事实，不是**用户的**事。她永远不认识和她说话的人——对纪念向产品，这是在场感的最大缺口之一。

## 改进方案

SQLite（与 P0-3 共库）存条目与来源。检索先用可解释的关键词/全文索引验证需求；若召回不足，再评估本地 embedding 模型和 `sqlite-vec` 向量索引。`fastembed` 负责生成向量，`sqlite-vec` 负责索引，两者不是互相替代项；向量维度由选定模型决定。

1. **写入**：用户启用记忆后，在已确认提交的轮次异步抽取 0-2 条候选（如「用户叫小林」「用户下周要考试」），带 kind 与来源消息 ID；抽取完成前不阻塞 SSE，但只有写入事务成功才视为已保存。候选是用户自述，不自动提升为已核实事实。
2. **检索**：`prepare_chat_messages` 组上下文时，除现有 persona RAG 外再取 top-k（k=3-5）用户记忆，得分 = 相似度 × 时间衰减（half-life 按 kind 配置：身份长、事件短）+ retrieval_count 强化；注入为 system 侧附加上下文。
3. **冲突与更新**：相似度只能找候选，不能独自判定矛盾；新说法明确否定旧说法时标记 superseded，其余交给用户查看/纠错。来源消息删除或 reset 时级联清除关联记忆。
4. **遗忘**：时间衰减控制检索优先级，不等于删除数据；提供单条删除、全部清除和关闭记忆的操作，并说明保留期限。

对齐 CONTEXT.md 约束：她记得的是「用户说过的事」，表述永远可以追溯到用户原话（每条记忆存 source 消息 seq），**不假装亲历记忆**（与「事实」词条的 Avoid 一致）；不进台词强制复述，只作召回依据。

## 验收

- 单测：衰减得分单调性、retrieval_count 强化、superseded 不召回、关闭/删除后不召回、抽取失败不污染已有记忆。
- 端到端剧本：告诉名字 → 聊别的 20 轮 → 重启（依赖 P0-3）→ 新话题里自然用对名字；盲测「记得我」无编造（说她记得的都是真说过的）。

## 边界与风险

- 抽取调用增加每轮一次 LLM 开销：用小模型/短 prompt，且仅在有新增价值的轮次触发（可先粗筛：消息里有人名/「我叫/我喜欢/我明天」类模式才跑）。
- 若选 embedding，默认本地模型；检索质量先对真实中文对话集评估，不能由「32 维起够用」预断。抽取若调用云端 LLM，用户自述会送往该服务，产品文案需如实说明。
- 本方向是「她对用户的记忆」，不做「她自己的经历记忆」（airi 的方向）——那是另一个产品决策，v1 不扩。

## 规模

M-L（存储 + 抽取 prompt 调优 + 检索注入 + 盲测）。
